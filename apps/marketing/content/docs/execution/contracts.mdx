# Execution contracts

```js
import { run } from 'captar';

const result = await run(
  'repair',
  {
    limits: { durationMs: 30_000, resources: { 'db.writes': 100 } },
    outcome: { verified: { equals: 1 } },
  },
  async (execution) => {
    const reservation = execution.reserve('db.writes', 1);
    // Await your database operation here.
    execution.commit(reservation);
    execution.metric('verified', 1);
  }
);
```

`reserve` checks committed plus reserved usage before admitting work. `commit` records actual usage; an actual amount above the ceiling is reported, not silently clamped. `release` returns unused reserved capacity. `consume` and its alias `count` immediately charge resource usage.

Use `metric(name, value)` for outcome assertions (`min`, `max`, `equals`). Missing required metrics fail the outcome. `checkpoint(name, value)` records application progress; it does not make the database write and receipt save atomic.

`durationMs` aborts `execution.signal`. Underlying operations must honor cancellation; the library cannot preempt arbitrary JavaScript or roll back completed effects. A receipt captured at a deadline may retain reservations for in-flight work.

Only guarded operations count. Resource names and estimated amounts are supplied by your application. Budgets apply to each execution, not to every process in a fleet.

## Check capacity without failing the run

**Repository feature, not yet published to npm.** `checkResource(resource, amount = 1)` returns a read-only capacity decision. Unlike `reserve`, an insufficient-capacity result does not fail the execution or add a violation. This lets a worker finish gracefully when it has no room for another item.

```ts
const decision = execution.checkResource('db.writes', 1);
if (!decision.allowed) {
  // Stop taking new work, or choose a smaller batch.
  return;
}

const hold = execution.reserve('db.writes', 1);
// Await your idempotent write here.
execution.commit(hold);
```

The result includes `resource`, `requested`, `committed`, `reserved`, `allowed`, and `reason`. Limited resources also include `limit` and `remaining`. Reasons are `within-limit`, `unlimited`, `resource-limit`, or `not-running`. Pending reservations count against capacity. Terminal executions cannot admit more work, even for an unlimited resource. Invalid names or non-positive/non-finite amounts throw without mutating the run.

A check is a point-in-time observation, **not a hold on capacity**. Always call `reserve` before the operation; concurrent work can use capacity after the check. Stopping gracefully still has to satisfy any outcome rules you configured. An early stop does not automatically create or persist a checkpoint.
